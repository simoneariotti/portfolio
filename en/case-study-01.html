Askme Design System: from zero to AI-ready

Three years of a system built from scratch for an enterprise suite, and the strategy to make it readable by artificial intelligence.

01 · Context

Three products, one designer, no system.

I joined as product designer in a suite whose three modules had grown independently: no shared components, no common language, no design system. I built it from scratch, and have owned it for three years.

  • ScopeVariables, shared components, cross-module patterns and the branding guidelines that sit on top.
  • What this case coversTwo arcs: building the system, and the work in progress to make it readable by AI.
  • The point of itNot order. Askme is not three products side by side: it is a platform where the module is the unit it answers the market with. The system lets a new one be born already consistent, and lets every feature be designed inside known constraints.
What Askme is

Askme is a B2B enterprise platform for business process automation: service management, legally binding electronic signature and native conversational AI. It is used by organisations in finance, industry, energy, healthcare, higher education and public administration.

02 · The problem

Divergence, then divergence at the speed of AI.

Three products, three histories, one brand. Every new feature reinvented patterns that already existed somewhere else in the suite: consistency held on a single feature, cracked at module level, and broke completely between one module and another.

  • The priceIt was not an aesthetic one. Every new module restarted from the shape instead of from the problem: the look of a button went back up for discussion while the market waited for a feature. On a platform that grows by adding modules, divergence is paid in time.
  • Then the acceleratorAI-assisted development let teams ship interfaces without going through design. The output was usable, but every generated screen used its own patterns, duplicating components that already existed. Divergence at the speed of AI.

03 · The reasoning

Patterns that survive futures nobody has drawn yet.

Building the system: the first three years

The Askme component library started from nothing. Every piece answered an immediate need, but was already shaped by the system that would grow around it. It is dense work up front that pays back later: adding a feature rarely meant rewriting the ones before it.

From file upload to cross-module navigation, from form controls to Sign signatures: a whole library, still in production today. Two examples tell it better than a list.

  • Adaptable containers. Containers, dialogs and expansion panels built as archetypes: they hold data, images, complex cards, inputs, anything. Not one component per case, but a single form that holds cases nobody has specified yet. Same containers, always different contents.
  • A table that removes noise. Tables are everywhere in Askme. The custom one, with advanced filters and saved views, gives every user or their manager the view they need: more focus on their own work, less noise, always the same recognisable pattern. On mobile it degrades into usable cards, deliberately leaving the more complex functions out.

Neither would have survived without the part you do not see: a single library shared with engineering, naming that matches on both sides, decisions taken together rather than handed down. A large share of a system's value lives in that hinge.

Making it readable by AI: the work in progress

The same AI push that fuels the divergence is what makes a system AI can read necessary.

The system was designed for the recipient it had: a person. Specifications written for handoff with engineering, in prose a developer reads, components built to work on screen. It was human ready, legible to whoever had to use it, and it was the right choice for the requirement of the time.

Then the recipient doubled, and a machine does not read the prose of a specification: it reads structure. Names that do not match the ones in the code, variant and property structure decided case by case, duplicate sets left in circulation: to a person these are frictions you read your way around, to an agent they are ambiguities it gets wrong. The AI-ready project did not discover a badly built system, it changed the criterion by which it is judged. Today I am rebuilding the internal structure of components I considered closed: not the interface, which holds, but the way they are built inside.

If everyone uses their own AI with their own patterns, divergence multiplies. If the AI reads the design system, that same speed becomes convergence. The strategy I proposed and am now executing:

  • Portability before lock-in. Foundations converted to the W3C DTCG standard for tokens: readable by any tool, not trapped in a single vendor.
  • Two layers, two owners. A semantic layer (design's, tool-independent) kept strictly separate from a code-binding layer (engineering's). They never mix.
  • An automated token pipeline. From the design tool to a versioned repository through to generated code, with automatic pull requests. One source of truth instead of two that slowly drift apart.
  • Components explained to a machine. Naming that matches the code library, semantic descriptions, reference implementations: so the AI picks the right existing component instead of inventing a lookalike.
  • An explicit boundary between core and extension. What every module shares and what belongs to one alone, declared rather than implied.

For a person

The loading indicator signals that something is under way and cannot be shown yet. It comes in two sizes: the small one sits inside a button or next to a label, the large one in the middle of the area that is loading. Its colour is the secondary text colour, never the module's, because it is a system signal and not a piece of identity. If the wait goes past two seconds it must carry text saying what is happening, otherwise it stays silent. It is not used for percentages: that calls for a bar, not a spinning circle.

The same component, documented both ways. The component is invented and the values are placeholders: the structure, the field names and their order are the real ones. The entry is wrapped to fit the column, and it is left in Italian because that is the language the index is written in.

This entry is tidy because I took it from the most frequent shape, and it would be dishonest to let you think the whole file looks like this. Field names and their order change from entry to entry, several fields appear on little more than half of them, and the schema declared at the top of the file does not list everything the file actually uses. Even inside the field meant to remove literal values a few survive: the gap: 8 above is one. The structure holds and it is not settled yet, and saying so is more useful than showing only the clean example: it is the difference between a system that measures itself and one that presents itself.

The strategy closes with a falsifiable pilot: given only the design system, can an AI compose a new, consistent module? Explicit success criteria, and the stated freedom to return an honest “not yet”. Presenting it as an experiment rather than a promise is what made the proposal credible.

What made the answer possible is documentation written for a machine rather than for a person: a structured index of the components, a catalogue explaining how they combine, a sheet for each one. And a closed release cycle, from the design file to the package for engineering to publication in the repository, with a human check before the last step.

The visual deep-dives come as diagrams redrawn in abstract form: patterns and structures, not real product interfaces.

04 · Outcome

One language, and analysis that starts from constraints instead of from the shape.

The modules today share one design language, a single component library across design and code, and branding guidelines built into the system instead of propped up beside it. The AI-ready strategy was written as one document for two audiences at once, a proposal for whoever decides and a reference guide for whoever executes, and it is now being carried out.

The pilot answered yes: from the design system alone, an agent recomposes consistent modules. On more involved cases not yet, and it is the pilot itself that shows where.

The destination is not consistency for its own sake. It is that a new module is born quickly without putting the shape back up for discussion, and that every new feature is designed inside constraints that are already defined: analysis starts from a known set of pieces instead of from a blank page, and what is left to decide is the problem. It is also the difference between a system that declares itself ready and one that can say what it is not ready for.

05 · The measurement

For three years I knew where it hurt, not by how much.

I governed it by judgement, and that worked while the system was small. In September 2026 I measured it, from the design file through to the code generated from it, with the method stated beside every number.

Measurement, September 2026

  • 124live components in the current scope
  • 93of those have a written specification: three out of four
  • 221icons, all on the same 24-pixel grid

Method: top-level components and variant sets on the pages the file itself declares as the system's scope; icons excluded from the count and measured separately. Every count resolves to the identifier of the source component and never to its name: in the file five components are called File and two different sets are called Buttons, so counting by name gives a plausible, wrong number.

The perimeter only says what is there. The useful question is a different one: is the system actually used, and how much of it survives into the code? Five indicators.

  • 01Canonical component adoptionHow many instances use the official component instead of a predecessor still in circulation.
  • 02Instances repainted by handHow much the system gets worked around instead of extended.
  • 03Components with a specificationHow many are documented well enough to be used by someone else, or by a machine.
  • 04Instances hanging off external librariesHow much of the system moves when someone else moves.
  • 05States that reach the codeHow many of the properties declared in design survive code generation.

Measuring them was the uncomfortable part. A system without numbers defends itself with enthusiasm, and as long as nobody looks everyone is right. Now they have a date and a repeatable method: the next measurement compares against this one, and from there every indicator has a direction instead of an opinion. Where the system is weakest, and what I chose to raise first, I am happy to go through in person: those numbers belong to someone else's product.

A principle that emerged

The consistency of a system is not the one you draw: it is the one that survives the people who use it and the code generated from it.
